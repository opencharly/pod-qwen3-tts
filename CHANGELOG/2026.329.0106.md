# 2026.329.0106 — fix(gate): read free VRAM through NVML, not the nvidia-smi CLI

## Summary

The free-VRAM gate exec'd `nvidia-smi`. That binary is **not** part of the container runtime's GPU
contract — measured inside a deployed pod of this very image:

```
$ charly cmd check-qwen3-tts-pod "sh -c 'ls -l /usr/bin/nvidia-smi 2>&1; ls -l /usr/lib/libnvidia-ml.so.1 2>&1; ls /dev/nvidia*'" 
ls: cannot access '/usr/bin/nvidia-smi': No such file or directory
-rwxr-xr-x 1 nobody nobody 2958776 Nov  3 01:58 /usr/lib/libnvidia-ml.so.1
/dev/nvidia-modeset
/dev/nvidia-uvm
/dev/nvidia-uvm-tools
/dev/nvidia0
/dev/nvidiactl
```

The runtime injects **the NVML library and the device nodes**; the CLI is an extra that the full CDI
spec happens to add (`nvidia.com/gpu=all` in the live deployment does have `/usr/bin/nvidia-smi`).
So the gate refused every synthesis in the deployment that had the library but not the CLI, with
`503 gpu_unavailable` — `nvidia-smi was not found, but QWEN3_TTS_DEVICE=cuda:0 requires an NVIDIA
GPU`.

**The gate now reads NVML directly** (`ctypes`, ~60 lines):
`nvmlInit_v2` → `nvmlDeviceGetCount_v2` → `nvmlDeviceGetHandleByIndex_v2(QWEN3_TTS_GPU_INDEX)` →
`nvmlDeviceGetMemoryInfo` → free MiB. Same bounded-wait semantics, same env knobs, no NVIDIA tooling
required, and it works wherever the runtime injected the library.

Env changes (every option still settable by env, with a documented default):

- **removed** `QWEN3_TTS_NVIDIA_SMI` — it named a binary that is not part of the contract;
- **added** `QWEN3_TTS_NVML_LIB` (default `libnvidia-ml.so.1`);
- **added** `QWEN3_TTS_GPU_FREE_MIB` — a **diagnostic** override of the reading, unset in every
  deployment, used by the tests so they need neither a GPU nor a CLI.

The docs also lose the false claim PR #13 added ("the image must ship `nvidia-smi` … compose
`layer-nvidia`"): the pod/driver contract forbids baking driver user-space or an NVIDIA binary
(`pod-cdi`/`layer-cdi` fail such a build), and trying it failed `check-image` on `layer-nvidia`'s
dead assertion. Both surfaces now state the real contract.

**What this run proves about the change** — the gate's data source now works in the container shape
that broke it. The service's own NVML readings appear in its release log, in-container:

```
qwen3-tts: speech worker released (idle for 31.6s); free VRAM 11138 -> 13633 MiB
```

and the gate-refusal step (a second shim at a 999999 MiB floor, 2 s deadline) PASSES, which requires
a real reading. Neither was possible with the CLI-based gate in this container.

**The two failures are NOT this change**, and neither is silently deferred:

- `qwen3-tts-synthesis` returns **500** because the worker cannot initialise CUDA in that container:
  `AssertionError('libcuda.so cannot found! …')`. Measured there: the device nodes and
  `libnvidia-ml.so.1` are present, `libcuda.so.1` is not — while the same box deployed with
  `charly config`/`start` has `nvidia-smi` and a working `libcuda`. Filed as **opencharly/charly#1280**
  with that evidence and a remedy (the bed deploy leg must apply the same CDI spec the normal deploy
  applies).
- `qwen3-tts-idle-unload` failed on its OWN script: it called `nvidia-smi` to compare free VRAM.
  That assumption was mine in the consumer bed and is wrong for the same reason as this PR's subject;
  the bed now reads `vram_free_mib` from the service's `/health` (the same NVML reading), committed in
  the consumer tree.
